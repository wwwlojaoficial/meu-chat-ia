02 / TUTORIAL PASSO A PASSO

Como reproduzir a investigação no PC

Segue a organização técnica do tópico enviado. As etapas descrevem o processo e o raciocínio de análise; os offsets do post não devem ser copiados para outra versão do cliente.

Identificar a build

Registre versão do APK, arquitetura, nome da biblioteca nativa e hash SHA-256. Isso permite saber se duas análises realmente usam o mesmo binário.

Abrir a biblioteca no disassembler

Carregue libqplay.so no IDA ou Ghidra, selecione ARM64/AArch64 e deixe o analisador terminar antes de interpretar pseudocódigo.

Procurar strings e referências

O autor procurou strings associadas a execução de scripts e eventos, abriu referências cruzadas e acompanhou as funções chamadoras. Uma string isolada não prova a função da rotina.

Confirmar com análise dinâmica

O Frida permite observar o fluxo em tempo de execução. Compare chamadas normais do jogo e anote entradas/saídas, sem assumir que a assinatura inferida está correta.

Entender o formato do script

O motor não recebe necessariamente texto GS2 puro. No cliente investigado, TScript::setStream lê uma stream binária com cabeçalho, funções, strings e comandos.

Separar bytecode e objeto

O artigo descreve o bytecode como dados que precisam ser associados a um objeto de script. Criar o objeto e preparar o contexto são etapas distintas.

Mapear a entrega de eventos

O autor investigou por que alguns eventos chegavam e outros não. Definir uma função não basta: ela precisa ser reconhecida e o evento deve ser roteado ao objeto certo.

Validar sem misturar mudanças

Faça uma alteração por vez, mantenha cópia do APK original e registre o resultado. Para o crash atual, capture o stack trace antes de gerar outra versão da interface.

Compatibilidade: o tópico parece usar builds próximas de 701652/701752; o projeto atual usa 701030. Os offsets, layouts e assinaturas do post são referências históricas, não endereços garantidos para o seu binário.
03 / CONTEXTO DA VM — DETALHADO

O que é o contexto e por que ele é essencial

Esta parte combina o conceito descrito no tópico com os resultados anotados no arquivo de contexto do projeto Graal Classic 2.2.

VM (Virtual Machine): interpreta o bytecode e executa operações GS2.

TScript: representa o script carregado e mantém funções/comandos compilados.

TScriptFunction: representa uma função do script, incluindo metadados necessários para chamá-la.

TScriptSpace: espaço de script associado a um objeto/contexto; recebe o script, instala os capturadores de evento e pode disparar o evento de criação.

TGraalVar: valor/objeto do motor. No estudo atual, TGraalVar+0x50 foi identificado como o campo de TScriptSpace no caminho de TGraalVar::setScript.

TScriptMachine: máquina de execução temporária. O fluxo observado prepara o objeto em execução, prepara a função, adiciona tokens/argumentos à stack e chama o interpretador.

TScriptSpace::executeFunction @ 0x2393AC
  ├─ TScriptUniverse::getFreeMachine()              @ 0x239408
  ├─ TScriptMachine::setExecutingObject(...)        @ 0x239440
  ├─ TScriptMachine::prepareScriptFunctionExecution @ 0x23945C
  ├─ TScriptMachine::stackAddTokens(TGraalVar*)      @ 0x23948C
  ├─ TScriptMachine::executeScript()                 @ 0x239498
  ├─ TScriptMachine::clearExecuteScript()            @ 0x2394B0
  └─ TScriptUniverse::addToFreeMachines(...)         @ 0x239534

Conclusão registrada: chamar executeScript() isoladamente não é suficiente. A rotina de alto nível prepara máquina, objeto e stack antes de executar e depois limpa/devolve a máquina ao conjunto de máquinas livres.

O recurso estudado começou com bytes zlib/DEFLATE. Após descompressão, a stream tinha 5107 bytes e incluía nomes como onCreated e propriedades de GUI. A análise concluiu que a stream não é código-fonte GS2 puro; é um formato binário proprietário.

O arquivo de contexto registra que TScript::setStream (@ 0x224CD8, tamanho anotado de 2400 bytes) reseta o script, cria uma lista de strings, usa uma parser table e lê cabeçalho/comprimentos. Processa tipos identificados como 2, 3 e 4: funções, strings e bytecode/comandos TScriptCom; depois chama addFunction().

A tabela do parser foi localizada em 0x2F655C. O contexto anota marcadores F0–F6 e suas conversões. Isso é análise da stream do binário específico, não uma especificação universal de GS2.

TScript::addFunction (@ 0x223C08) verifica nomes, trata nomes com ponto como eventos capturados e cria/adiciona objetos TScriptFunction à estrutura de funções. TScript::getFunction procura funções registradas. TGraalVar::getScriptedFunction procura uma função já registrada; não compila fonte GS2 digitada.

O contexto anota campos de TScriptFunction em offsets +0x70, +0x78, +0x7C, +0x80 e +0x88. Esses offsets só se aplicam à build estudada.

TScriptSpace::setScript(TScript*) instala event catchers e, se houver funções, chama invokeCreatedEvent(). Este chama receiveEvent(...), que percorre a lista de capturadores e pode ativar o script do objeto.

O tópico relata que inicialmente onCreated e onTimeout eram observados, mas onPlayerChats não era disparado no objeto criado. Isso mostra que reconhecer o nome de uma função, registrar o evento e receber o evento real são problemas diferentes.

O contexto identifica elementos TScriptCom com opcode em +0x00, TStringEncoded em +0x08 e um double em +0x10; cada elemento da array tem 0x28 bytes. Foram inspecionados, entre outros, handlers associados a opcodes 0x15, 0x16, 0x17, 0x18, 0x19, 0x1A, 0x14 e 0x32.

Os handlers observados manipulam a stack, tipos de valores, chamadas de função, comparação/fluxo e atribuição. O opcode é interpretado através de uma jump table. A lista não deve ser generalizada para outra versão sem nova análise.

O botão atual apenas recebe o clique e lê o texto da interface. Para uma execução real, o texto teria de passar por um compilador compatível para produzir bytecode; depois esse resultado precisaria ser carregado no formato aceito, associado a um objeto válido, registrar as funções/eventos e ser executado com contexto/stack corretos.

Estado atual: o arquivo de contexto diz que a compilação fonte → bytecode, o pipeline completo do botão e a execução real ainda não foram concluídos. O painel visual não comprova um executor funcional.

04 / SCRIPTS DO TUTORIAL

Exemplos GS2 e fragmentos explicados

As capturas contêm exemplos de Frida/NativeFunction e leitura de memória específicos do processo. Abaixo estão exemplos GS2 educacionais e a finalidade dos fragmentos mostrados, sem transformar offsets de outra build em um injector pronto.

GS2 · exemplo 01

Evento de criação

function onCreated() {
  echo("Script iniciado");
}

Modelo básico para estudar a entrada de evento. A sintaxe e disponibilidade de echo devem ser verificadas no ambiente de GS2 usado.

GS2 · exemplo 02

Evento periódico

function onCreated() {
  echo("Preparando teste");
}

function onTimeout() {
  echo("Timeout recebido");
}

Declarar onTimeout não agenda automaticamente um timeout. O objeto precisa receber o evento pelo mecanismo do ambiente.

GS2 · exemplo 03

Evento de chat

function onPlayerChats(player, message) {
  echo("Evento de chat recebido");
}

Esqueleto para estudar entrega de eventos. A assinatura de parâmetros depende da versão e do contexto do script.

GS2 · exemplo 04

Evento de mouse

function onMouseDown() {
  echo("Clique recebido");
}

O tópico usa onMouseDown como ponto de partida para investigar a propagação de eventos no motor.

Caso separado das capturas

Função r() ausente

Uma das imagens parece mostrar uma discussão de script que chama r(requestOptions), mas a função não foi definida. A resposta sugeriu um stub para modo offline:

function r(options) {
  return null;
}

Isso apenas devolve um valor vazio. Não implementa HTTP nem substitui os dados esperados pelo script. A imagem não prova que esse caso faça parte do tutorial principal do executor.

Frida · conceito mostrado

createGraalString / readGraalString

As capturas mostram helpers para converter entre strings JavaScript e a representação de string do motor, com leitura de comprimento e ponteiro. O layout e a ABI dependem da build. Um erro no tamanho ou no ponteiro pode encerrar o processo.

Frida · conceito mostrado

getGraalHash / function lookup

O autor descreve um hash de nomes e uma rotina de busca em tabela para localizar funções. A ideia importante é que a busca depende da convenção interna de nomes; localizar uma função não significa compilar ou executar texto novo.

Frida · conceito mostrado

Bytecode, objetos e eventos

O tópico relata tentativa de observar bytecode após o carregamento e investigar a função de execução. O autor afirma que a primeira tentativa com bytecode próprio falhou e que precisou estudar a criação do objeto e o roteamento de eventos.

Sobre os scripts nativos das capturas: os fragmentos usam NativeFunction, endereços base + offset, leitura de ponteiros e hooks de funções internas. São específicos de uma build e podem quebrar o cliente. Por isso esta documentação explica seu papel e limitações, mas não empacota os hooks/dumpers de memória em um script pronto para alterar o jogo.

Handlers inspecionados: 0x14, 0x15, 0x16, 0x17, 0x18, 0x19, 0x1A e 0x32. As notas associam alguns deles a números, strings/valores, chamada de função, controle de fluxo e atribuição.
