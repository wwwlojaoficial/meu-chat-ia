03 / TUTORIAL

Aprenda em módulos

O que aparece nas capturas é separado do que ainda precisa ser confirmado no projeto.

GS2 é a linguagem de scripts do Graal. Estude variáveis, funções, eventos e APIs documentadas. A documentação descreve usos client-side e server-side, além de referências de funções e GUI. Consultar GS2.

Meta: explicar um script simples e reconhecer funções do ambiente Graal.

Nas capturas, o autor diz que usou um compilador GS2 externo. O contexto ASPEC descreve a stream como formato binário, não texto puro. Fonte, bytecode e objeto de script são coisas diferentes.

O contexto registra que TScriptSpace::executeFunction obtém uma máquina, define o objeto em execução, prepara a função, adiciona tokens à pilha e então chama o interpretador. Isso indica que o contexto importa.

O tutorial menciona eventos como onCreated, onTimeout e onMouseDown. Localizar uma função não é a mesma coisa que registrá-la ou receber o evento.

O contexto identifica o cliente 701030 e avisa que as versões do tutorial parecem posteriores. Endereços e offsets podem mudar entre builds; registre versão, arquitetura e hash do binário.

O painel visual aparece dentro da cópia modificada do cliente, mas o botão ainda não executa GS2 real. A tentativa de interface flutuante causou crash; o contexto recomenda obter o stack trace antes de outra alteração.

06 / BIBLIOTECA DE SCRIPTS

Scripts GS2 — exemplos comentados

Agora há exemplos de GS2 para estudar e um mapa do código mostrado nas capturas. Os exemplos GS2 são modelos educacionais; o laboratório do site não está conectado ao cliente.

Script 01 — inicialização

Exemplo mínimo para estudar o evento de criação e a saída de texto.

function onCreated() {
  echo("ASPEC: script iniciado");
}

O nome do evento precisa ser reconhecido pelo ambiente em que o script roda. Este exemplo não prova que o executor customizado está funcionando.

Script 02 — temporizador

Modelo para compreender um evento periódico. A disponibilidade exata de sleep e a sintaxe de agendamento dependem do ambiente GS2.

function onCreated() {
  echo("Temporizador iniciado");
  // Configure o evento periódico
  // usando a API documentada do seu ambiente.
}

function onTimeout() {
  echo("Evento de timeout recebido");
}

O evento onTimeout só ocorrerá se o motor registrar/agendar o timeout para esse objeto.

Script 03 — mensagem recebida

Esqueleto para estudar eventos de chat. A assinatura dos parâmetros varia por contexto.

function onPlayerChats(player, message) {
  echo("Evento de chat recebido");
  // Inspecione player/message conforme
  // a documentação da versão usada.
}

O artigo cita onPlayerChats; não garante que esse evento seja disparado em todo tipo de objeto de script.

Script 04 — clique

Modelo para entender o evento de mouse em contextos que o suportam.

function onMouseDown() {
  echo("Clique recebido pelo script");
}

O artigo descreve o rastreamento de onMouseDown como caminho para investigar a propagação de eventos.

Importante: os quatro exemplos acima são scripts GS2 de estudo, não um executor pronto. O site não tem compilador GS2 integrado e não envia esses scripts para o jogo.
07 / TUTORIAL COMPLETO DO CONTEXTO

Como o contexto de execução se encaixa

Esta seção detalha o que as capturas sustentam, separando as observações do autor das conclusões que ainda precisam ser verificadas no cliente ASPEC.

O contexto é o conjunto de estado que permite ao motor executar uma função de script: referência ao objeto/script atual, função/evento em andamento, valores temporários e estado da máquina virtual. Não é apenas o texto do script. Uma função nativa encontrada no binário pode depender de um contexto válido e de parâmetros preparados pelo próprio motor.

Implicação para o ASPEC: ter o código-fonte em uma caixa de texto não cria, por si só, um objeto de script válido, não compila GS2 e não fornece o contexto exigido pelo interpretador.

Fonte GS2
   ↓ compilador compatível
Bytecode GS2
   ↓ criação/configuração do objeto de script
Objeto + contexto da VM
   ↓ registro de eventos/funções
Evento ou chamada de função
   ↓ interpretador do motor
Efeito/resultado no ambiente

Este é um diagrama conceitual do fluxo. A captura diz que o autor usou um compilador de terceiros e que encontrou uma rotina interna que associa um objeto de script ao bytecode. Isso não significa que os offsets apresentados sejam válidos na versão do ASPEC.

No contexto do projeto, essa rotina foi descrita como preparando a VM/objeto, selecionando a função, colocando tokens/argumentos na pilha e chamando o interpretador. Em termos práticos, a chamada precisa receber os tipos, ponteiros e estado que o motor espera. Invocar uma rotina interna com uma assinatura presumida pode causar corrupção de estado ou crash.

Checklist de investigação: confirme a versão/build; identifique a chamada a partir de referências cruzadas; examine quem prepara os argumentos; registre o fluxo de retorno; compare com uma execução normal de script; valide em ambiente de teste controlado.

Um objeto de script é a entidade que o motor gerencia. Uma função é uma entrada que pode existir dentro desse objeto. Encontrar uma função pelo nome não prova que ela esteja registrada como evento, nem que o objeto tenha sido incluído na lista de scripts ativos. As capturas descrevem uma tabela/lista de objetos e um caminho separado de registro de eventos.

O autor relata que inicialmente só observava onCreated e onTimeout, enquanto onPlayerChats não chegava ao objeto. Depois investigou a origem do evento de mouse e o caminho de propagação pelo gerenciador de scripts. A lição é que definir uma função com o nome certo não basta: o evento precisa ser emitido, roteado e registrado para o objeto correto.

Diagnóstico: teste um evento por vez; registre se a função foi reconhecida; verifique se o objeto está ativo; compare com um script nativo equivalente; diferencie falha de compilação de falha de registro e de falha de entrega do evento.

As capturas mostram o autor investigando valores passados pela pilha e a conversão de um valor de tipo interno para uma string GS2. Também aparece uma rotina auxiliar para criar uma string do formato esperado pelo motor. Isso sugere que a representação de strings/valores do jogo não deve ser tratada como uma string JavaScript comum.

Não copie endereços de memória ou layouts de estruturas de outra build. Uma diferença no tamanho, alinhamento, tipo ou propriedade do ponteiro pode produzir falhas difíceis de diagnosticar.

Uma das capturas parece mostrar uma discussão separada sobre um script que chama r(requestOptions), mas essa função não está definida no script. A resposta mostrada propõe um stub que retorna null para permitir um modo offline. Isso apenas evita a chamada ausente; não implementa rede nem recupera a resposta esperada.

// Stub ilustrativo para teste offline,
// não é uma implementação HTTP:
function r(options) {
  return null;
}

Use esse stub somente quando o script aceitar explicitamente uma resposta vazia. Se o código espera campos da resposta, ele ainda pode falhar. A captura não comprova que essa função faça parte do tutorial principal do executor; trate-a como um caso separado.

O artigo relata a observação de uma rotina que devolvia dados de bytecode após o carregamento/descriptografia de um script e uma tentativa posterior de substituir bytecode durante o carregamento. O próprio autor diz que a primeira tentativa de executar bytecode próprio falhou e que continuou investigando a criação do objeto de script.

Bytecode não é intercambiável sem verificar cabeçalho, versão, tamanho, formato e compatibilidade do compilador. A página não inclui um compilador funcional nem validação binária para o cliente 701030.

As imagens contêm exemplos de NativeFunction, endereços base + offset, leitura de ponteiros e hooks de funções internas. Esses trechos estão ligados a uma build específica e dependem de ferramentas e layouts de memória que não foram confirmados para a versão usada pelo ASPEC. Por segurança e para evitar crashes, esta página não transforma esses fragmentos em um script pronto para injetar/hookar o cliente.

Para documentar sua build, registre versão, arquitetura, hash do binário, nome da biblioteca, hipótese da função, evidência usada e nível de confiança. Não reutilize offsets apenas porque o nome da função parece semelhante.

Uma captura descreve strings armazenadas com uma chave XOR de três bytes gerada no início do processo, aplicada de forma repetitiva. O trecho ilustrado lê a chave e aplica XOR byte a byte. Isso é uma descrição do formato observado pelo autor, não uma prova de que toda string ou toda versão use o mesmo esquema.

Para análise legítima de um arquivo de teste próprio, valide primeiro com entradas e saídas conhecidas. Não aplique offsets ou chaves extraídos de outra versão sem confirmar o layout.

O contexto do ASPEC identifica o cliente como versão 2.2 / código 701030 e a biblioteca libqplay.so. As capturas do fórum mostram outra build/ambiente. Endereços, ABI, estruturas, eventos e assinaturas podem mudar. A semelhança de nomes não garante equivalência.

Ordem recomendada: obter logcat/stack trace do crash; reproduzir sem overlay; confirmar biblioteca e arquitetura; documentar uma hipótese por vez; só então testar mudanças pequenas. Não altere vários componentes de uma vez.

  • Um compilador GS2 compatível com a versão-alvo e sua licença/atribuição verificadas.
  • Uma forma documentada de carregar/validar o resultado sem presumir offsets.
  • Criação válida do objeto e do contexto exigidos pelo motor.
  • Registro e entrega de eventos verificados separadamente.
  • Logs de erro e testes sem overlay antes de retomar a interface flutuante.

Até esses pontos serem demonstrados, o painel continua sendo uma interface visual, não um executor funcional.
